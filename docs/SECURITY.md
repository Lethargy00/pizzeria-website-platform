`bootstrap-lockfile` (#129) is the one workflow that runs dependency code (`pnpm install --ignore-scripts`, Prettier) and pushes to `main`. It does so in two jobs, both only for `refs/heads/main`: `generate` (`contents: read`, no persisted credentials) runs that code and uploads a patch; `push` (`contents: write`, `actions: write`) runs only checkout, download-artifact, bash, coreutils, grep, git and gh, applies the patch, rejects it unless it only adds or changes `pnpm-lock.yaml` or modifies ordinary non-code formatted files (Markdown, JSON, YAML, CSS), then pushes. Refused: dot paths, `scripts/`, `tenants/`, `e2e/`, manifests, tool config, and every path that `scripts/review-gate.mjs` sends to architect, dependency, security or richtext review (including `packages/core/src/richtext/**` and `packages/*/src/contracts/**`). `scripts/test/workflow-bootstrap-lockfile.test.mjs` asserts this, and fails if a tracked file or a sample of any matrix glob is a reviewed path the job would accept.

Because `generate` runs dependency code, the push job also treats the content of the patch as untrusted (#177):

- **Code is never auto-pushed.** A change to a code file (`.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.astro`, `.mdx`, `.html`, `.htm`, `.vue`, `.svelte`) fails the run, even outside the protected paths. Format it in a reviewed PR; `ci` runs `format:check` on every PR, so this only happens when `main` is already unformatted.
- **Lockfile sources.** Every `tarball` in the patched `pnpm-lock.yaml` must be on `https://registry.npmjs.org/`. Every git, URL, `file:` or `link:` line must already be in the base lockfile under the same parent keys, so the existing workspace `link:` entries stay and a new one, or one moved to another importer or package, fails the run. A plain `deprecated:` message, which may contain a URL, is exempt from this check.
- **Lockfile form.** The lockfile is checked as text, so it must be in the plain style pnpm writes. Anchors, aliases, tags, merge keys, document markers (which a `%` directive needs), explicit keys, block scalars (with or without a trailing comment), tabs, carriage returns, backslash escapes, Unicode line breaks, double quotes outside a `deprecated:` message (pnpm writes single quotes), and `{...}`, `[...]` or single quotes that do not close on the same line all fail the run, because they could hide an entry or move it to another parent. With only one quote character allowed, a line that opens a multi-line quoted value always has an odd number of them.

A lockfile change that fails these checks, such as a new git or workspace dependency, goes in a reviewed PR. Residual risk: the job does not check which registry package versions or integrity hashes the lockfile pins, so a compromised `generate` could still pin a different published version of a transitive dependency. The `security` workflow's audit runs on the pushed commit.

## Rules for every change

- Tenant input is validated with the shared Zod schemas; unknown keys are errors.
- No raw HTML from tenant content; Markdown through the allow-list sanitizer; URL schemes `https:`, `mailto:`, `tel:` only.
- CSP: no `unsafe-inline`, no `unsafe-eval`. New origins only through a platform adapter that a tenant enabled.
- No secrets in the repo. Each adapter ships a `.env.example`; real values live in hosting or GitHub environment secrets, scoped per tenant.
- No PII in logs, fixtures or test data. Demo data is fictional.
- Never weaken a control to make a test pass (PROMPT.md §10).

## Recommended repository setup (Q8.4)

Apply when the plan allows it (see `docs/HANDOFF.md`):

1. **Branch protection / ruleset on `main`:** require a pull request; require status checks `ci / guards`, `ci / build-test`, `pr-gates / review-gate`, `pr-gates / touches-guard`, `security / gitleaks`, `security / deps`; require branches to be up to date; block force-pushes and deletion; include administrators.
2. **Two-person review on `main`** for `packages/`, `.github/` and `scripts/` via CODEOWNERS (`.github/CODEOWNERS`).
3. **Per-role identities:** move from one shared account to one GitHub App per role (orchestrator, architect, security, …). Then `approved:<role>` labels can be replaced by real GitHub approvals, and `review-gate` can check the approver's identity. Until then approvals rest on signed comments and Orchestrator verification (residual risk T13).
4. **Private vulnerability reporting** enabled; **Dependabot alerts and security updates** enabled.
5. **Environments** `staging-<slug>` and `production-<slug>` with required reviewers for production, holding per-tenant secrets.

## Supply chain

- One lockfile at the root; CI installs with `--frozen-lockfile`.
- Every dependency change needs a `type:dependency` issue approved by `architect` and `security`, an exact version and an entry in `docs/DEPENDENCIES.md`.
- GitHub Actions: pin to full commit SHAs with a version comment (`uses: actions/checkout@<sha> # v4.x.y`). Open finding until done; Dependabot (`github-actions` ecosystem) then keeps SHAs current.

## Dependabot PRs

Dependabot PRs pass through `touches-guard` with an exception (#59). Two things matter to maintainers:

1. **Do not use "Update branch" on a Dependabot PR.** That button adds a commit that is not Dependabot's, so the commit check fails. To rebase the PR, comment `@dependabot recreate` instead.
2. **The commit check cannot prove a commit came from Dependabot.** A commit made through the Contents or Git Data API with the bot as author is still signed by `web-flow`, so it passes. The real defence is the dependency path allow-list plus the review gate, which always requires `approved:peer` and `approved:security` on a Dependabot PR (and `approved:architect` for dependency files). Never treat a green touches-guard as proof of provenance.

The rules are repeated in the header comment of `scripts/touches-guard.mjs`.
